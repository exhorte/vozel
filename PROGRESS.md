## Déviations signalées (pas de nouvelle dépendance hors spec, mais écarts d'exécution à noter)
- `storage::settings::Settings` complété avec un champ `hotkey_mode: HotkeyMode` (absent du scaffold initial) — nécessaire pour rendre configurable le choix `PushToTalk`/`Toggle` explicitement demandé par `Spec_Backend_Desktop.md` §1.1 ("les deux modes... configurables dans les réglages"), qui n'avait qu'un champ `hotkey: String` pour la combinaison de touches. Défaut choisi : `Toggle` (plus simple à l'usage qu'un maintien, pas de décision produit tranchée ailleurs) — modifiable dès que `Spec_Frontend.md` Phase 1 §1.2 (panneau réglages) existe.
- Valeur par défaut de `hotkey` changée par rapport au scaffold initial (`"Fn"` → `"control+shift+Space"`) : `"Fn"` seul n'est pas enregistrable comme raccourci global sur la plupart des claviers laptop (touche interceptée par le firmware du contrôleur clavier, jamais délivrée à l'OS comme événement clavier normal — `RegisterHotKey` Win32 ne peut pas s'y accrocher). `"control+alt+Space"` testé en premier et rejeté aussi (déjà pris par une autre app/le système sur la machine de dev, et Ctrl+Alt = AltGr sur beaucoup de claviers non-US donc risqué comme raccourci global). `"control+shift+Space"` testé avec succès (enregistrement + cycle press/release complet, voir journal Session 2).
- Le CLI `shadcn` a été profondément redessiné depuis la rédaction de `Spec_Frontend.md` : il n'a plus de prompts "style" (New York/Default) ni "base color" au sens classique, mais un système de presets (Nova, Vega, Maia...) combinés à un choix de bibliothèque primitive (Radix UI / Base UI / React Aria). Preset retenu : **Nova** avec base **Radix UI** — c'est le plus proche des exigences explicites de la spec (Radix UI sous-jacent, icônes `lucide-react`, base color neutre — confirmé dans `components.json` : `"baseColor": "neutral"`, `"iconLibrary": "lucide"`). `components.json` contient `"style": "radix-nova"` au lieu de `"new-york"` — à garder en tête si un futur `npx shadcn add` se comporte différemment de ce que la spec suppose.
- **(Session 7) Déclencheur UI manuel de la dictée sur le `FloatingWidget`** — pas une étape numérotée de `Spec_Frontend.md`, ajout demandé explicitement par l'utilisateur (le §1.6 backend mentionnait déjà « depuis l'UI (bouton) » sans qu'aucun élément d'interface ne l'appelle). Le widget entier devient `role="button"` (clic + Entrée/Espace) et appelle `startDictation`/`stopDictation`, **les mêmes commandes IPC que le hotkey** — pas de chemin d'état parallèle. A nécessité un petit écart côté backend (voir entrée suivante) pour que les deux déclencheurs partagent réellement le même état.
- **(Session 7) `PipelineState` gagne un drapeau `listening: Arc<AtomicBool>`** partagé entre le thread du hotkey et les commandes IPC. Le mode `Toggle` du hotkey gardait jusque-là son propre booléen interne : démarrer/arrêter la dictée depuis l'UI le désynchronisait (le raccourci demandait alors un appui « fantôme » pour se recaler — bug confirmé empiriquement avant correctif). `start_dictation`/`stop_dictation` sont désormais idempotentes et mettent à jour ce drapeau, que le hotkey lit pour décider. Écart minime et local, cohérent avec l'intention « une seule source de vérité » déjà présente dans le code.
- **(Session 7 suite, §2.1) `sqlx` en direct plutôt que `tauri-plugin-sql`.** La spec §2.1 nomme le plugin SQL de Tauri mais autorise explicitement `sqlx::migrate!` comme alternative pour les migrations. Choix `sqlx` direct validé avec l'utilisateur : **tout l'accès à la base est côté Rust** (les réglages passent par des commandes IPC ; le dictionnaire §2.2 s'applique dans `postprocess::cleanup`, appelé depuis `run_pipeline`) — un `SqlitePool` possédé dans l'état managé (`storage::db::Db`) + `sqlx::migrate!` est plus simple et moins fragile que l'accès au type semi-interne `DbInstances` du plugin (alignement de version de `sqlx`, `block_on` dans des commandes sync). Le plugin apporterait surtout une API JS SQL, inutile ici puisque le frontend passe par IPC. Dépendance ajoutée : `sqlx` (features `runtime-tokio`, `sqlite`, `migrate`, `macros`).
- **(Session 7 suite, §2.1) Échec d'ouverture de la base SQLite = fatal au démarrage** (`setup` renvoie `Err`, l'app ne démarre pas). Rupture assumée avec le pattern Phase 1 « ne jamais planter » appliqué au micro / modèle ASR / fichier de config absents — mais ces cas-là sont des absences légitimes et recouvrables au premier lancement, alors qu'une base illisible que l'app crée elle-même dans son propre dossier de données inscriptible signale un environnement cassé (disque plein, permissions, corruption) où continuer à moitié (sans réglages ni dictionnaire) n'apporte rien. Un message d'erreur clair au démarrage vaut mieux.
- **(Session 7 suite, `Spec_Frontend.md` §2.1) Formulaire d'ajout/édition du dictionnaire : formulaire contrôlé simple au lieu de `react-hook-form` + `zod` + shadcn `form`.** La spec cite ce trio comme « pattern recommandé par shadcn pour le composant `form` », pas comme une exigence. Le formulaire a deux champs texte (`from`, `to`), une validation triviale (non vides — bouton désactivé sinon) et l'unicité de `from` est vérifiée côté backend (`storage::dictionary`, message d'erreur clair renvoyé et affiché en toast). Trois dépendances supplémentaires ne se justifient pas ici ; cohérent avec les choix « minimal, justifié » du reste du projet. À revoir si un futur panneau a un formulaire réellement complexe.
- **(Session 7 suite, §2.4) Client HTTP `ureq` + `multipart/form-data` construit à la main.** La spec parle de « streaming HTTP » ; l'endpoint transcription de Groq (comme celui d'OpenAI) n'est **pas** un flux — c'est un `POST` fichier-entier / réponse-JSON unique. `ureq` (sync, sans runtime) plutôt que `reqwest` : `AsrEngine::transcribe` est synchrone et `run_pipeline` s'exécute sur un thread bloquant (thread du hotkey ou pool de commandes IPC) — `reqwest::blocking` risquerait un « runtime dans un runtime » si un appelant devenait `async`. Le corps multipart (un champ `model` + un fichier `file`) est assez trivial pour être écrit à la main, ça évite une crate de plus. Encodage `f32` → WAV PCM16 fait à la main aussi (en-tête de 44 octets ; `hound` n'est qu'une `dev-dependency`).
- **(Session 7 suite, §2.4) `AsrState` passe de `Option<LocalAsrEngine>` à `Option<Box<dyn AsrEngine + Send + Sync>>`** (l'aiguilleur `RoutingAsrEngine`). Le **seul** changement dans `commands/` est la suppression d'un `use crate::asr::AsrEngine;` devenu mort (les méthodes de trait sur un `Box<dyn Trait>` n'exigent pas le trait dans le scope) — pas un changement de logique. Le critère §2.4 « aucun changement dans `commands/` » vise le fait que le pipeline ne connaît pas le choix local/cloud : c'est bien le cas, `run_pipeline` appelle `engine.transcribe(&pcm)` à l'identique.
- **(Session 7 suite, `Spec_Frontend.md` §2.3) `Select` au lieu du `combobox` pour le fournisseur cloud.** ~~Choix temporaire (un seul fournisseur branché).~~ **Résolu en Session 15** : les 3 fournisseurs étant maintenant tous implémentés (§2.4.3), le `Select` est remplacé par un vrai `Combobox` shadcn (`command` + `popover`), conforme à la spec §2.3 point 1. Le sélecteur de **moteur ASR local** (`id="asr-engine"`) reste un `Select` — la spec §1.2 ne demande pas de combobox là, et `whisper-cpp` y est toujours désactivé (non branché).
- **(Session 7 suite, §2.4) `Settings` : `Debug` réécrit à la main pour masquer `cloud_api_key`.** La spec demande « jamais en clair dans les logs ». Un `#[derive(Debug)]` afficherait la clé via n'importe quel `{:?}` (log, message de panic). Le `Debug` manuel rend `cloud_api_key: "<défini>"` ou `"<vide>"`. La clé reste stockée **en clair dans `vozel.db`** (fichier privé du dossier de données de l'app, hors dépôt) — un chiffrement au repos (DPAPI Windows / trousseau) serait un durcissement ultérieur, non couvert par §2.4.
